# Quickstart — validating apidelta

**Feature**: [spec.md](./spec.md) · **Plan**: [plan.md](./plan.md) · **Date**: 2026-10-16

How to run the feature and how to tell whether it actually works. Every scenario below maps to a success
criterion in the specification, so this file doubles as the acceptance walk-through. It is a run guide, not
an implementation guide: shapes live in [data-model.md](./data-model.md) and
[contracts/](./contracts/application-ports.md).

---

## Prerequisites

- .NET 10 SDK.
- No Azure DevOps server, no network, no credentials. This is the first tool in the toolbox that needs
  none — if the shell still demands a server address before reaching the **OpenAPI** tab, R11 was not done.

```bash
dotnet build DevToolbox.slnx          # warnings are errors: a warning is a failed build
dotnet test DevToolbox.slnx
dotnet run --project src/DevToolbox.Console
```

Then: **OpenAPI** tab → **apidelta**.

---

## The corpus

Validation needs documents with known answers. They live as embedded resources under
`tests/DevToolbox.Tests/Tools/ApiDelta/Corpus/` and are small enough to read by eye, except the last two.

| File | What it is for |
|---|---|
| `baseline-30.yaml` | a valid OpenAPI 3.0.3 production description: 7 operations, vendor extensions at document and operation level, a path with four operations, path-level parameters shared by them, a global security requirement and one operation that opts out of it — the shape Scenario 11 needs |
| `baseline-30.reformatted.yaml` | semantically identical, written differently: four-space indentation, reordered top-level keys, unquoted response codes, reordered `required` sets, added comments. CRLF is applied by the loader rather than stored, since line endings do not survive a repository reliably |
| `baseline-30.json` | the same document as JSON, hand-written rather than converted, to prove format is not difference |
| `baseline-31.yaml` | a compact 3.1 description with union-with-null nullability and an unknown vendor keyword inside a schema |
| `candidate-additive.yaml` | one new optional parameter, one new operation, one new schema |
| `candidate-breaking.yaml` | a removed response, two narrowed `maxLength` constraints, a newly required parameter, a removed enum value |
| `candidate-doc-only.yaml` | a corrected description, summary and contact name |
| `candidate-conflict.yaml` | the `Dossier` component keeping its name while changing its required set and gaining a property |
| `candidate-path-removed.yaml` | one path removed, for the removal side of a correction |
| `broken-duplicate-key.yaml` | the same mapping key twice, with different values |
| `broken-unresolved-ref.yaml` | a `$ref` to a component that does not exist, used in three places |
| `broken-version.yaml` | `openapi: 4.0.0` |
| `cyclic.yaml` | schemas that reference each other |
| `redundant.yaml` | 14 identical inline header parameters, 6 identical error responses, 2 identically shaped schemas under different names, 3 unreachable components, an operation described as obsolete without the deprecation flag, an optional request body, mixed response-code quoting |
| `secrets.yaml` | a bearer token in an example and a password in a server URL |
| *(generated)* | `GeneratedDescription.Wide(1000, 10000)` — the SC-003 subject, about 3.5 MB |
| *(generated)* | `GeneratedDescription.Deep(200)` — nesting past the configured depth limit |

Each candidate is derived from `baseline-30.yaml` by one documented edit, so the difference under test is
the only difference present.

The last two are generated by `GeneratedDescription` rather than committed, so that a clone does not carry
megabytes to serve two tests. The generated wide description also chains its schemas — each references the
next — which is what exposed the reference walk's missing depth bound (R18).

## Scenario 1 — formatting is not difference (SC-001)

Compare `baseline-30.yaml` against `baseline-30.reformatted.yaml`, then against `baseline-30.json`.

**Expected**: zero differences, version recommendation **none**, `outcome.code` `clean`. The report's
differences sections are present and empty.

**If it fails** the normalization table (R6) is wrong, and every other result is suspect — this is the
first scenario for a reason.

---

## Scenario 2 — breaking, additive, documentary (SC-005)

Compare each of `candidate-breaking.json`, `candidate-additive.json` and `candidate-doc-only.json` against
`baseline-30.yaml`.

**Expected**: major / minor / patch respectively; each difference carries a location, a classification, a
rationale and a recommended action; each breaking change names what breaks; the version section lists the
contributing changes. Nothing is classified `non-breaking` that removes or narrows anything.

---

## Scenario 3 — refusal (SC-009, spec US2)

Run an audit on `broken-duplicate-key.yaml`, then `broken-unresolved-ref.yaml`, then `broken-version.yaml`.

**Expected**, in all three: a located diagnostic, the run fails, and **no artifact is written** — check the
output directory is empty. For the duplicate key, both positions are reported. For the unresolved
reference, all three using locations are listed. For the version, the supported range is stated.

Then `cyclic.yaml`: the audit **completes**, the cycle is not an error, and the process does not stack
overflow (SC-011).

---

## Scenario 4 — the audit (spec US5)

Audit `redundant.yaml`.

**Expected**, at minimum: `AUD-100`/`AUD-101` grouping the 14 headers into **one** finding with 14
locations and a byte estimate; `AUD-102` on the error responses; `AUD-003` on the three unreachable
components; `AUD-205` on the obsolete description without the flag, as `REVIEW_REQUIRED`; `AUD-007` on the
optional request body, as `REVIEW_REQUIRED`; `AUD-202` on the mixed quoting, as `SAFE`; `AUD-104` reporting
the two same-shaped schemas under different names as `REVIEW_REQUIRED`, never `SAFE`.

Every finding carries a rule identifier, a severity, a safety class, a location and a recommended action.
The result screen shows the rule-outcome count, and any rule that could not run is on the summary.

---

## Scenario 5 — the plan, then the application (SC-007, SC-008, SC-012)

Optimize `redundant.yaml`, plan only. Record the production file's hash first.

**Expected**: a plan with savings, break-even counts and safety classes; the production file
**byte-identical** afterwards; no optimized document written.

Now run it again with *appliquer ce qui est sûr*.

**Expected**: `openapi-production.optimized.yaml` plus a manifest; production still byte-identical; the
optimized document reparses, revalidates and verifies contract-equivalent; `REVIEW_REQUIRED`
transformations present in the plan and **absent** from what was applied; every vendor extension still
present (SC-010); the measured saving within 10% of the estimate.

Then the negative half: inject a transformation that alters the contract (the test harness has a hook for
this) and confirm **no file is published** and the outcome is `outputFailure`.

---

## Scenario 6 — resume (SC-015)

Start an *everything* run on `large-1000.yaml`, let it reach the audit step, then `Ctrl+C`.

**Expected**: the run stops, nothing half-written exists, and the next launch offers the run for resume
with its labelled selection. Resume it: both files are read again, and the artifacts match those of an
uninterrupted run outside the run-metadata block.

Then edit one input by a single byte and try to resume: **refused**, with the reason. A resumed comparison
of a changed file is the one answer a resumable tool must never give.

---

## Scenario 7 — scale (SC-003)

Audit `large-1000.yaml`.

**Expected**: under 30 seconds on a developer workstation, progress visible throughout, the run reporting
its own duration. Then audit `deep.yaml`: refused with the depth limit named, not a stack overflow.

---

## Scenario 8 — determinism (SC-004)

Run the same *everything* run twice into two directories, then compare.

```bash
diff -r artifacts-a artifacts-b        # differs only inside the run-metadata block
```

**Expected**: identical except the delimited run-metadata block. If anything else differs, a collection is
being written in hash-table order somewhere (see [contracts/artifacts.md](./contracts/artifacts.md) §2).

---

## Scenario 9 — secrets (SC-016)

Audit `secrets.yaml`, then read every artifact and the log file.

**Expected**: a finding naming the location and the pattern of each secret-shaped value; **the values
themselves appear nowhere** — not in the report, not in the JSON, not in the log, not in the checkpoint.
`grep` the artifacts and the log for the literal token; zero hits is the test.

---

## Scenario 10 — configuration (spec US8)

Audit `redundant.yaml` with a ruleset that sets `AUD-101.minimumOccurrences: 20`, disables `AUD-204`, and
raises one severity. Then add a suppression for `AUD-007` without a justification, and finally one with a
justification and an expiry in the past.

**Expected**: the header finding disappears below the threshold; `AUD-204` is reported as disabled; the
unjustified suppression is **invalid configuration** and the run does not start; the expired suppression
reports both the finding and the expiry. Suppressed findings appear in their own section with justification
and owner.

---

## Scenario 11 — extract one route (SC-017, SC-018, spec US9)

Pick `baseline-30.yaml` and the extract mode, then select one operation that shares its path with others,
inherits path-level parameters, is covered by the global security requirement, and references a chain of
schemas — `GET /documents/{id}` in the corpus is built to be exactly that.

**Expected**: `openapi-extract.yaml` containing that operation and no other; the path item carrying the
inherited parameters; the global security requirement and only the scheme it names; the tag definitions it
uses and no others; every schema in the chain, each once; `info.version` identical to the source; the
`x-apidelta-extract` provenance stamp at the root; and the source file byte-identical afterwards.

Then the exhaustive form, which is the actual criterion: extract **every** selectable operation of
`baseline-30.yaml`, one run each, and assert for all of them that the extract reparses, validates, resolves,
contains nothing unselected, and is contract-equivalent in effective form to the same operation in the
source (SC-017).

Then two negatives: select nothing and confirm the run is refused with an explanation rather than producing
an empty file; and break the builder so it drops a path-level parameter, and confirm verification fails,
names the operation and the missing parameter, and publishes nothing.

Finally the scale half: on the generated 1,000-operation document, filter by tag and by path fragment and
confirm a named route can be found and selected without reading the list (SC-018).

## The gate before calling it done

```bash
dotnet build DevToolbox.slnx                                  # zero warnings
dotnet test DevToolbox.slnx
dotnet test DevToolbox.slnx --collect:"XPlat Code Coverage"
```

- Architecture tests pass, including the new assertion that `ApiDelta.Core` depends on neither YamlDotNet
  nor Microsoft.OpenApi, and that `Presentation` does not reference `Infrastructure`.
- `CompositionRootTests` resolves the real graph, so a rule written but never registered fails CI.
- The mutation suite is green: no breaking mutation classified non-breaking, no transformation over one
  classified `SAFE` (SC-002).
- The checkpoint-shape test still passes, and the new one asserting a serialized apidelta checkpoint
  contains no document content.
- Golden artifacts are approved and reproduce byte-for-byte.
